SERVER BENCHMARK — bloewecalc (AMD EPYC 9454P, 48 cores / 96 threads) vs office (Ryzen 9 7950X)
==================================================================================================
Date: 2026-09-28 (evening). Script: server ~/Overcharged/bench/bench.sh, log bench.log.
Build: same code and flags on both machines (gcc -O3; server gcc 13.3).

CPU CLOCK STATE DURING THE BENCHMARK
  Driver acpi-cpufreq, max scaling frequency 2.75 GHz (base); boost to 3.8 GHz not used.
  A busy core read ~2.35 GHz. The governor was schedutil, switched by the user to performance
  during the 32-run point (no measurable effect: busy core still 2.35 GHz), and was back to schedutil
  at the end. -> The 1/16 points were not rerun: the governor doesn't change the clock under this driver.
  The real fix is the amd-pstate driver or a BIOS boost/power profile (user to ask jacuna).

     server : 312.5 s   0.80 MPUPS      -> 2.4x slower per run (clock ~2.35 vs ~5+ GHz)

          1           0.327            0.6 MPUPS
         16           0.415            7.7 MPUPS
         32           0.495           12.9 MPUPS
         48           0.485           19.8 MPUPS
         96 (SMT)     0.669           28.7 MPUPS
   office reference: 1 run 0.153 s/step (1.3 MPUPS); 9 runs ~0.30 s/step (~6.1 MPUPS total).

CONCLUSIONS
  - Throughput keeps rising up to all 96 hardware threads: SMT helps (the code is memory-latency
    bound; a second thread hides stalls). 96 runs at once give ~4.7x the office machine's total
    throughput; 48 runs give ~3.2x.
  - Each run is slower: 0.67 s/step at 96 at once, vs 0.15 s/step alone on the office machine
    (~4.4x). The largest runs therefore set the finish time of a sweep.
  - Recommendation: run sweeps with up to 96 at once, largest jobs first (jobs.txt order),
    so the long runs start immediately and the small ones fill in around them.
    ρ ≥ 0.10 main sweep (3 seeds): total work ~ 0.4 day at 96-way; finish time set by the largest
    runs (R ≈ 64, ~6.6 h alone on office) ≈ 20–30 h on the server.
  - Memory is no constraint (188 GB; a 200k-particle run needs ~40 MB).
  - After the driver/boost fix: rerun bench.sh. Expect ~1.4x per run from 2.35 -> ~3.3–3.8 GHz, but
    less at full load (power-limited) — the 96-way point is the one to compare.
